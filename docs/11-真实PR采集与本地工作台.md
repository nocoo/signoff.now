# 11 — 真实 PR 采集与本地工作台

本阶段把真实 Azure DevOps PR 接入 10 的工作台。第一期只做 PR；GitHub 与 issue / work item 的工作台接入仍在后续阶段。既有 Activity / Score 管线的命令和表保持独立。

## 数据链路

```text
Projects（organization / project / repositories）
  → Worker collection_jobs
  → 本地 signoff workbench sync / watch
  → az account get-access-token + ADO REST API（只读）
  → @signoff/domain 的统一 PullRequest
  → 分批 collection_staging
  → 按采集范围原子发布 pull_requests + scan_runs
  → Web 队列、卡点、policy、build、stage
```

数据库由 Wrangler 管理，位置为 `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/*.sqlite`。`0012_live_collection.sql` 增加仓库范围、采集任务、暂存区和采集器心跳；`0013_visible_pr_collection.sql` 为任务保存 PR 选择范围，schema version 为 13。线上 D1 可以使用相同 SQL 结构；本阶段只运行本地迁移与采集。

PR 采集客户端只接受 `localhost`、`127.0.0.1`、`[::1]` 的 Worker origin。Worker 采集路由限制在开发入口，生产 pipeline token 的白名单不扩展。Azure 访问令牌只留在 CLI 内存和 Azure CLI 自己的凭据缓存，不传给 Web 或数据库。

## 使用

```bash
bun run db:migrate:local
bun run dev:worker
# 另开终端
bun run dev
# 另开终端；已有有效 az 登录时直接运行
bun run dev:collector
```

在 Projects 添加 organization、project 和可选仓库名。仓库名用逗号分隔，留空代表所有仓库；新增项目始终为真实来源，即使本地 Demo 开关已开启。编辑采集范围会废弃旧任务并清理旧范围的快照，避免把不同来源的数据拼在一起。暂停监控保留已发布快照。

一次性导入仓库 URL 并采集：

```bash
bun run signoff workbench sync --repo \
  'https://dev.azure.com/acme/Platform/_git/web-app' \
  'https://dev.azure.com/acme/Services/_git/api'
bun run signoff workbench sync
bun run signoff workbench watch
```

重复注册相同 URL 不会重复创建项目；注册同一项目下的新仓库会扩展已有范围。已有“所有仓库”范围不会被缩窄。`watch` 每 3 秒处理界面队列，不再自行安排全项目扫描；`sync` 和界面手动 Scan 保留完整扫描。Web 空闲时按配置间隔刷新，默认每 2 分钟；已提交且尚未结束的任务每 3 秒更新进度（包括等待登录恢复），即使自动刷新已关闭。

## 当前页采集

`POST /api/projects/:id/scan` 使用当前 `revision`，可选的 `pullIds` 区分三种范围：

| 请求范围 | 采集与发布行为 |
| --- | --- |
| 省略 `pullIds` | 手动完整扫描，发现 PR 并读取全部检查 |
| `pullIds: []` | 只发现 PR 列表与基础状态，不请求 policy、build、timeline 或变更统计 |
| 非空 `pullIds`，最多 20 个且不重复 | 直接请求这些 PR 并丰富详情，不枚举其他仓库 / PR，发布时保留范围外快照 |

Auto refresh 可选关闭 / 1 / 2 / 5 / 10 分钟，默认 2 分钟，保存在 `signoff-auto-refresh-seconds` localStorage。仅在 Live、PR 页面可见、采集器已连接时自动排队。列表和检查按所选间隔判定是否过期，未采集检查可立即加载；目标为当前页全部 PR（每页 20 个），与滚动位置无关，不预取其他页。翻页后切换采集范围；通过链接打开不在当前页的 PR 详情时，单独加载该 PR。导航后延迟 600ms 开始检查，每 5 秒重试到期工作，同一项目至少间隔 15 秒才再次请求；隐藏标签页、离开 PR 页面、翻页、修改筛选或刷新设置后，停止旧范围尚未提交的自动请求；已提交任务仍可完成并显示进度。采集器连接状态按快照取得时的心跳判断，避免较长刷新间隔造成误报离线。

列表发现保留 PR 的 `headSha`。只有新旧非空 SHA 相同时才复用已缓存检查，且保留原始 `checksObservedAt`；提交变化或缺少 SHA 时，检查保持未采集，不能据此判为可合并。界面显示检查实际采集时间。定向详情更新不会改变项目的列表扫描时间，也不会删除未选中的 PR。

## 认证与恢复

- CLI 验证真实 ADO token 的存在和有效期，不把 `az account show` 的缓存账号信息当成登录成功。
- 访问 ADO 组织时读取组织的租户提示，必要时通过匿名 HEAD 获取 `x-vss-resourcetenant`，再使用 `az account get-access-token --tenant ... --resource ...` 获取目标租户的 token。
- token 接近过期时静默续期；遇到 401 或登录跳转只重试一次。不会把登录页解析成成功的 JSON 数据。
- 需要用户重新登录时显示 `auth_required` 和 `az login --tenant ... --scope 499b84ac-1321-427f-aa17-267ca6975798/.default` 提示。重新登录后 watch 自动恢复排队任务。
- 403 权限不足、404 仓库不存在、网络故障和无效响应分别报告；不把所有失败归为登录过期。CLI stderr 中的 token 或凭据不会进入登录错误消息。

## 快照与状态

采集全部开放 PR，近期历史按仓库限制为最多 20 条已合并、10 条已关闭。开放 PR 分页不能静默截断；必要的范围枚举失败时不发布不完整的 PR 列表。policy 和 timeline 等详情缺失可以发布 `partial`，页面会列出缺失原因，缺失检查不能令 PR 变成可合并。

统一契约中必需门禁与 advisory 检查分开，历史 status 和 build 重试需取当前结果，构建阶段来自 ADO timeline；没有 Stage 记录的构建使用 Job 记录。超过 100 个阶段/Job 的大型构建保留全部记录，上传大小由请求字节数限制。group reviewer 的汇总票不会额外算作一个人的批准。无法取得的文件数、增删行数、评论数保存为 `null`，界面明确显示不可用。

`collection_jobs` 的状态为 `queued`、`running`、`auth_required`、`complete`、`partial`、`failed`。任务绑定项目 revision 和随机 lease token，每次进度或上传续租；租期为 120 秒。客户端定时续租，进程退出后过期任务可重新领取。

每批最多上传 20 个 PR，并受请求字节数限制；这些行只进入暂存区。所有行上传完成、声明数量与暂存数量一致后，再用 D1 batch 原子发布。每条依赖 SQL 都验证任务归属、租约和项目 revision；任何并发编辑、取消、过期领取或失败都不能覆盖新的项目范围。上传中断、登录过期和失败保留上次已发布的 PR。

## 界面与边界

- 应用全局顶栏使用无可见标签的 Live / Sample 分段切换，跨 PR / Projects 页面生效；存在真实项目时默认 Live，否则默认 Sample。旧的 All data 链接回到默认来源，不混合真实与示例统计。
- ADO 按 Organization → Project → Repository 联动筛选，Project 显示实际 ADO 项目名。切换上级会清除下级范围，直接选择仓库会补齐父级；URL 保存 `org`、`project`、`repo`。例如 `msdata / Vienna / online-meetings` 和 `intentional / intent / whiteboard-app` 分别统计。
- Sample 使用相同三级结构，GitHub 示例为 `github.com / nocoo / signoff.now`。Draft 默认排除，也可全部包含或只看 Draft；作者多选，默认全部。所有筛选保存在 localStorage，URL 中明确指定的筛选优先；兼容旧 `status=draft` 链接。
- 仓库通过下拉框筛选，开放 PR、待处理、构建中与可合并数量统一显示在汇总区。仓库身份同时包含所属项目和仓库 ID；配置中尚无 PR 的仓库也可筛选。
- Projects 展示配置的仓库范围、最近扫描、排队与进行中的 PR 数、错误和恢复提示。
- 各页面使用 Basalt PageHeader 的主标题、次标题和 AppHeader 的全局面包屑；分类来自侧栏导航，无跳转目标时不可点击；完整 Basalt Breadcrumbs 放入 AppHeader 的 leading 槽，由实际页面标记 `aria-current="page"`，避免组件将末尾祖先误当当前页。PR 页主标题固定为 Pull requests，次标题显示组织 / 项目 / 仓库路径，移除仓库横幅。采集动画与进度位于右下角，登录过期和失败仍可见。
- PR 表格与详情使用真实 policy、build、stage 和评审；PR 编号和真实 PR 标题旁有在新标签页打开源 PR 的链接，详情支持跳转原始 build。作者、负责人和评审者使用圆形双字母头像。
- About this change 渲染 Markdown（表格、任务清单、列表、代码、链接与图片），跳过原始 HTML，拒绝危险 URL。相对链接基于源 PR 解析，正常链接在新标签页打开。
- 项目 Readiness 设置包含从最就绪到最不就绪的完整状态列表，可拖动或用键盘箭头调整顺序、选择颜色。已采集的必需 Policy 可添加独立规则与显示名；按完整名称匹配，忽略首尾空白与大小写。没有内置 PoP 处理，原始失败 / 运行 / 等待状态不变。PR 有多个问题时由最不就绪的规则决定主项，同一个 build 中不同未完成 stage 状态也参与判断。
- 表格的标题、Readiness、检查完成比例、下一步、更新时间列头可排序；默认按各项目配置的 Readiness 顺序最就绪优先，同级按最近更新时间。`sort` / `direction` 一起保存到 URL 和 localStorage，旧 `sort=attention` 转为新默认。
- Migration 0014 为 `projects` 增加 `readiness_rules_json` 和 `readiness_revision`。`PATCH /api/projects/:id/readiness` 接收 `{ revision, rules }`，单条 SQL CAS 只修改这两个字段；最多 50 项，重复或缺失通用状态、无效颜色均拒绝。设置变更不影响 CLI 任务 revision、租约、扫描历史或 PR 快照；并发修改返回 409，重新打开设置后重试。
- 当前工作台读取最多 1,000 个 PR，超出时显示截断提示。该限制属于展示层；数据库保留完整采集结果。
- 当前没有 PR activity 时间线或增删行数的完整采集；没有获得的字段不生成示例值。GitHub CLI 接入、远端采集认证和部署另行实现。

## 验证

沿用仓库 TDD 和覆盖率门禁，测试包含登录过期/续期/租户切换、PR 分页与去重、policy 和 build 归一化、timeline 可空元数据、未知字段、分批上传、租约抢占、项目修改时的 CAS、失败快照保留、来源筛选和排队提示。timeline 的 task 记录可以包含 `identifier: null`，这种正常元数据不会导致同一构建的 stage 被丢弃。

新增回归覆盖：筛选缓存与全局来源、默认 20 条分页、刷新间隔默认值与持久化、整页采集与隐藏页暂停、翻页切换、未提交请求取消与无其他页预取、详情独立采集、claim 目标必须匹配请求、范围外上传拒绝、定向发布保留其他 PR、同 SHA 缓存复用与时间一致性、消失的目标结束任务而不循环领取、项目 Readiness 隔离与并发保存、多问题优先级、规则编辑与颜色验证、列排序方向持久化、Markdown 语义渲染与不安全内容。

```bash
bun run test:coverage
bun run lint
bun run typecheck
bun run build:web
bun run security
```

实际验收使用已授权 ADO 仓库：CLI 枚举数量与独立 `az repos pr list` 对账，Worker / SQLite 读取的开放数量一致；浏览器检查真实来源默认值、项目切换、PR 详情、build / stage、登录恢复提示和窄屏。真实私有响应、身份与截图只保存在忽略目录或本机临时目录，测试 fixture 使用合成数据。
