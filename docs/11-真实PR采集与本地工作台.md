# 11 — 真实 PR 采集与本地工作台

> 本文记录当前已实现行为。观察列表、主动增删 / 终态淘汰和对外 Query CLI 的目标设计见 [14–18](14-collector-architecture.md)，尚未替换本文的页面范围采集机制。

本阶段把真实 Azure DevOps PR 接入 10 的工作台。第一期只做 PR；GitHub 与 issue / work item 的工作台接入仍在后续阶段。既有 Activity / Score 管线的命令和表保持独立。

## 数据链路

```text
Projects（organization / project / repositories）
  → Worker collection_jobs
  → 本地 signoff workbench sync / watch
  → az account get-access-token + ADO REST API（只读）
  → @signoff/domain 的统一 PullRequest
  → 分批 collection_staging
  → 按采集范围原子发布 pull_requests + scan_runs
  → Web 队列、卡点、policy、build、stage
```

数据库由 Wrangler 管理，位置为 `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/*.sqlite`。本章 PR 采集迁移到 0016：0012 引入真实采集，0013 保存 PR 选择范围，0014/0015 保存项目 readiness 与实际 merge requirements，0016 引入两组持久化刷新队列。仓库迁移现到 0018，新增目录与统计部分见 [13](13-成员目录与PR贡献统计.md)。线上 D1 可以使用相同 SQL 结构；本章的 PR 验收只运行本地迁移与采集。`dev:worker`（含 `dev:all` 的 Worker 入口）启动前自动应用本地迁移，避免拉取新代码后因缺表或缺列出现 500；不重置已有数据。

PR 采集客户端只接受 `localhost`、`127.0.0.1`、`[::1]` 的 Worker origin。Worker 采集路由限制在开发入口，生产 pipeline token 的白名单不扩展。Azure 访问令牌只留在 CLI 内存和 Azure CLI 自己的凭据缓存，不传给 Web 或数据库。

## 使用

```bash
bun run db:migrate:local
bun run dev:worker
# 另开终端
bun run dev
# 另开终端；已有有效 az 登录时直接运行
bun run dev:collector
```

在 Projects 添加 organization、project 和可选仓库名。仓库名用逗号分隔，留空代表所有仓库；新增项目始终为真实来源，即使本地 Demo 开关已开启。编辑采集范围会废弃旧任务、快照及 requirement catalogue；切换到另一个 ADO organization / project 时也清除旧来源的 readiness 规则，避免 policy ID 重号导致误配。只修改仓库范围保留同一项目的用户偏好，重新发现适用要求；只改名称、负责人等字段保留并发采集发布的最新扫描状态。暂停监控保留已发布快照。

一次性导入仓库 URL 并采集：

```bash
bun run signoff workbench sync --repo \
  'https://dev.azure.com/acme/Platform/_git/web-app' \
  'https://dev.azure.com/acme/Services/_git/api'
bun run signoff workbench sync
bun run signoff workbench watch
```

重复注册相同 URL 不会重复创建项目；注册同一项目下的新仓库会扩展已有范围。已有“所有仓库”范围不会被缩窄。`watch` 并行运行 list、details 两条处理循环，空闲时每 3 秒请求 Worker 调度并领取任务。`sync` 显式排入一次性完整扫描，只领取本次请求的完整任务，并按任务 ID 查询发布结果，不受工作台最近 20 条历史的显示上限影响；后台暂停的自动检查不能替代它，其他采集器占用项目时继续等待，失败或登录失效返回非零退出码。PR 详情里的刷新只请求该 PR 的检查。

## 两组刷新队列

Worker/D1 的 `collection_refresh` 保存每组队列的冷却时间、轮次与完成时间，CLI 负责驱动调度；浏览器定时器不决定列表采集。

| 队列 | 默认冷却 | 范围 | 后台行为 |
| --- | --- | --- | --- |
| List | 120 秒 | 全部已启用 ADO 项目的配置仓库，发现新 PR 与 merged / closed 状态 | 浏览器隐藏或关闭仍继续，需本地 collector 运行 |
| Checks | 300 秒 | 当前页全部 PR，最多 20 个，不预取下一页 | 隐藏时暂停待领取任务；正在采集的一个 PR 可完成 |

冷却从**上一轮全部任务完成后的最晚完成时间**开始，失败任务也会结束本轮；等待登录的任务保留本轮，恢复后继续。两组冷却独立，同组不能重叠。每个项目只允许一个任务运行，已到期的列表任务可在两个 PR 详情任务之间先执行，避免长时间详情采集阻塞列表发现。

进入前台时，空闲的 Checks 队列立即开始新一轮；若上一轮尚未结束则继续它。翻页、筛选或打开当前页外的 PR 会切换目标、取消旧页未开始的任务，等待正在运行的任务完成后采集新页。正常数据更新造成当前页成员变化，仅更新下一轮的目标，不重新启动本轮。浏览器每 15 秒续期一次 45 秒前台租约；隐藏、离开 PR 页面时立即报告。递增序列号拒绝同一视图迟到的心跳，防止旧请求覆盖新页面或隐藏状态。

List、Checks 各自可选关闭 / 1 / 2 / 5 / 10 分钟，设置持久化在 D1，`signoff-refresh-cooldowns` localStorage 缓存 `{ listCooldownSeconds, detailCooldownSeconds }`。连接状态和两组冷却设置位于 PR 页标题右侧，四个统计筛选按钮位于搜索卡片内部、搜索框上方。关掉自动队列后，手动刷新仍可执行。Web 在前台每 3 秒读取已有真实项目与采集任务的最新快照，返回前台立即读取；右下角分别显示两组整轮进度、暂停状态和可处理的错误。

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET | `/api/collection/refresh` | 读取两组状态与整轮进度 |
| PATCH | `/api/collection/settings` | 分别修改 list / details 冷却 |
| POST | `/api/collection/view` | 报告当前页 PR、前台状态与视图序列 |
| POST | `/api/collector/schedule` | collector 为指定队列结算完成轮次、安排下一轮 |

这些路由均仅供本机开发使用。

## 采集与发布范围

`POST /api/projects/:id/scan` 使用当前 `revision`，可选的 `pullIds` 区分三种范围：

| 请求范围 | 采集与发布行为 |
| --- | --- |
| 省略 `pullIds` | 手动完整扫描，发现 PR 并读取全部检查 |
| `pullIds: []` | 只发现 PR 列表与基础状态，不请求 policy、build、timeline 或变更统计 |
| 非空 `pullIds`，最多 20 个且不重复 | 直接请求这些 PR 并丰富详情，不枚举其他仓库 / PR，发布时保留范围外快照 |

列表发现保留 PR 的 `headSha` 与 `targetSha`。只有两个 SHA 均非空、分别与缓存一致且目标分支名称不变时才复用检查，保留原始 `checksObservedAt`，同时更新列表中最新的 reviewer 投票。作者是否计票与是否允许反对票随 policy 设置保留，即使作者首次加入 reviewer 列表也正确计数；必需 reviewer 的拒绝始终阻止合并。提交或目标分支变化、缺少 SHA 时，检查保持未采集，不能据此判为可合并。界面显示检查实际采集时间。定向详情更新不会改变项目的列表扫描时间，也不会删除未选中的 PR。

## 认证与恢复

- CLI 验证真实 ADO token 的存在和有效期，不把 `az account show` 的缓存账号信息当成登录成功。
- 访问 ADO 组织时读取组织的租户提示，必要时通过匿名 HEAD 获取 `x-vss-resourcetenant`，再使用 `az account get-access-token --tenant ... --resource ...` 获取目标租户的 token。
- token 接近过期时静默续期；遇到 401 或登录跳转只重试一次。不会把登录页解析成成功的 JSON 数据。
- 需要用户重新登录时显示 `auth_required` 和 `az login --tenant ... --scope 499b84ac-1321-427f-aa17-267ca6975798/.default` 提示。重新登录后 watch 自动恢复排队任务。
- 403 权限不足、404 仓库不存在、网络故障和无效响应分别报告；不把所有失败归为登录过期。CLI stderr 中的 token 或凭据不会进入登录错误消息。

## 快照与状态

采集全部开放 PR，近期历史按仓库限制为最多 20 条已合并、10 条已关闭。列表任务领取时附带数据库中已知开放 PR 的轻量身份；如果这些 PR 未出现在本轮开放或近期历史中，CLI 逐个读取其最新基础状态，不读取检查。即使两轮间合并数量超出近期历史窗口，也能正确结束原先开放的 PR。单条补查失败发布 partial 并保留其旧记录；列表发布保留未返回的历史快照。开放 PR 分页不能静默截断；必要的范围枚举失败时不发布不完整的 PR 列表。policy 和 timeline 等详情缺失可以发布 `partial`，页面会列出缺失原因，缺失检查不能令 PR 变成可合并。

统一契约中必需门禁与 advisory 检查分开，历史 status 和 build 重试需取当前结果，构建阶段来自 ADO timeline；没有 Stage 记录的构建使用 Job 记录。超过 100 个阶段/Job 的大型构建保留全部记录，上传大小由请求字节数限制。group reviewer 的汇总票不会额外算作一个人的批准。无法取得的文件数、增删行数、评论数保存为 `null`，界面明确显示不可用。

`collection_jobs` 的状态为 `queued`、`running`、`auth_required`、`complete`、`partial`、`failed`，`kind` 区分 list / details / full，`round_id` 关联自动轮次。自动详情每个 PR 一个任务，便于在 PR 之间暂停和让出列表采集机会。任务绑定项目 revision 和随机 lease token，每次进度或上传续租；租期为 120 秒。客户端定时续租，进程退出后过期任务可重新领取。采集发布不增加项目 revision；revision 仅用于配置变更，避免一个队列的正常发布使另一队列失效。

每批最多上传 20 个 PR，并受请求字节数限制；这些行只进入暂存区。所有行上传完成、声明数量与暂存数量一致后，再用 D1 batch 原子发布。每条依赖 SQL 都验证任务归属、租约和项目 revision；任何并发编辑、取消、过期领取或失败都不能覆盖新的项目范围。上传中断、登录过期和失败保留上次已发布的 PR。

## 界面与边界

- 应用全局顶栏使用无可见标签的 Live / Sample 分段切换，跨 PR / Projects 页面生效；存在真实项目时默认 Live，否则默认 Sample。旧的 All data 链接回到默认来源，不混合真实与示例统计。
- ADO 按 Organization → Project → Repository 联动筛选，Project 显示实际 ADO 项目名。切换上级会清除下级范围，直接选择仓库会补齐父级；URL 保存 `org`、`project`、`repo`。例如 `msdata / Vienna / online-meetings` 和 `intentional / intent / whiteboard-app` 分别统计。
- Sample 使用相同三级结构，GitHub 示例为 `github.com / nocoo / signoff.now`。Draft 默认排除，也可全部包含或只看 Draft；作者多选，默认全部。所有筛选保存在 localStorage，URL 中明确指定的筛选优先；兼容旧 `status=draft` 链接。
- 仓库通过下拉框筛选，开放 PR、待处理、构建中与可合并数量统一显示在汇总区。仓库身份同时包含所属项目和仓库 ID；配置中尚无 PR 的仓库也可筛选。
- Projects 展示配置的仓库范围、最近扫描、排队与进行中的 PR 数、错误和恢复提示。
- 各页面使用 Basalt PageHeader 的主标题、次标题和 AppHeader 的全局面包屑；分类来自侧栏导航，无跳转目标时不可点击；完整 Basalt Breadcrumbs 放入 AppHeader 的 leading 槽，由实际页面标记 `aria-current="page"`，避免组件将末尾祖先误当当前页。PR 页主标题固定为 Pull requests，次标题显示组织 / 项目 / 仓库路径，移除仓库横幅。采集动画与进度位于右下角，登录过期和失败仍可见。
- PR 表格与详情使用真实 policy、build、stage 和评审；PR 编号和真实 PR 标题旁有在新标签页打开源 PR 的链接，详情支持跳转原始 build。作者、负责人和评审者使用圆形双字母头像。
- About this change 渲染 Markdown（表格、任务清单、列表、代码、链接与图片），跳过原始 HTML，拒绝危险 URL。相对链接基于源 PR 解析，正常链接在新标签页打开。
- 项目 Readiness 设置列出从实际 ADO policy 配置与 PR 快照发现的全部 merge requirements，包括已经通过的要求。用户从“先解决”排到“最后合并步骤”，可拖动或用键盘箭头调整顺序、颜色和显示名。第一个未完成要求决定 PR 主项；仅剩靠后要求的 PR 排在前面。未配置顺序时采用默认严重程度，冲突、未知检查、草稿与终态仍保留原含义，没有内置 PoP 特例。
- 同类型、同名称的 policy 合并为一行，规范化空白与大小写，并显示底层 policy 数量；只有所有适用的原始评估通过，整组才通过。CI 按 pipeline definition 区分，同名但不同 pipeline 不合并。保存的旧 source-ID 规则映射到合并后的要求，保留首个已配置名称、颜色和顺序。存在实际 review 要求时不再额外添加通用 reviewer 条目；queued / rejected 的 reviewer policy 表示等待审核，不能显示成构建中或 CI 失败。
- 表格的标题、Readiness、检查完成比例、下一步、更新时间列头可排序；默认按各项目配置的 Readiness 顺序最就绪优先，同级按最近更新时间。`sort` / `direction` 一起保存到 URL 和 localStorage，旧 `sort=attention` 转为新默认。
- `PATCH /api/projects/:id/readiness` 接收 `{ revision, rules }`，每项为 `{ gateId, label, color }`，按 `readiness_revision` 做单条 SQL CAS；重复 gateId、超限或无效颜色均拒绝。设置变更不影响 CLI 任务 revision、租约、扫描历史或 PR 快照；并发修改返回 409，重新打开设置后重试。
- 当前工作台读取最多 1,000 个 PR，超出时显示截断提示。该限制属于展示层；数据库保留完整采集结果。
- 当前没有 PR activity 时间线或增删行数的完整采集；没有获得的字段不生成示例值。GitHub CLI 接入、远端采集认证和部署另行实现。

## 验证

沿用仓库 TDD 和覆盖率门禁，测试包含登录过期/续期/租户切换、PR 分页与去重、policy 和 build 归一化、timeline 可空元数据、未知字段、分批上传、租约抢占、项目修改时的 CAS、失败快照保留、来源筛选和排队提示。timeline 的 task 记录可以包含 `identifier: null`，这种正常元数据不会导致同一构建的 stage 被丢弃。

状态机回归覆盖整轮完成后计时、慢任务不重叠、两条 CLI 循环独立、20/21 个 PR 的范围边界、后台列表继续与详情暂停、前台立即开始/恢复、迟到心跳、翻页取消旧目标、同页数据变化不重启轮次、登录恢复、禁用与手动刷新、并发 schedule / claim。Worker 并发测试使用独立 SQLite 连接和同步屏障；事务测试脚手架不能靠嵌套 BEGIN 的假错误替代真实竞争。

数据与 readiness 回归覆盖超过历史窗口的 PR 关闭对账、列表不预取检查、head/target 缓存失效、新 reviewer 投票、作者不计票与组票去重、同名 policy 合并后全部通过才就绪、不同 pipeline 分离、旧配置映射、采集期间编辑不丢草稿、项目配置隔离与 CAS。既有筛选缓存、默认 20 条分页、列排序、Markdown 和界面可访问性测试继续保留。

```bash
bun run test:coverage
bun run lint
bun run typecheck
bun run build:web
bun run security
```

实际验收使用已授权 ADO 仓库：CLI 枚举数量与独立 `az repos pr list` 对账，Worker / SQLite 读取的开放数量一致；浏览器检查真实来源默认值、项目切换、PR 详情、build / stage、登录恢复提示和窄屏。真实私有响应、身份与截图只保存在忽略目录或本机临时目录，测试 fixture 使用合成数据。

真实审核状态的回归样本为 whiteboard-app #59382：两人审核策略不计作者本人批准，reviewer 组的汇总票不算另一个人；采集时只有一个有效个人批准，应显示缺少审核。CI 与 PoP 仍按各自当前源结果和用户顺序展示，不能据此假定 CI 已通过。部分历史 ADO build 已不可用时仍显示 partial，不伪造通过。
